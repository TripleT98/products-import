# Схема хранения схема БД

Сущности Doctrine, ограничения PostgreSQL и миграции. Контракт ответов описан в [OpenAPI](openapi.json), демонстрационные данные — в [fixtures](fixtures.md).

## Mapping и ограничения

Все четыре сущности используют PHP attributes Doctrine ORM. ID — PostgreSQL INTEGER GENERATED BY DEFAULT AS IDENTITY. Миграция `Migrations\Version20261101000100` транзакционная; ledger — doctrine_migration_versions. Эта служебная таблица исключена только из ORM schema validation. Мигратор использует отдельное соединение без фильтра ledger.

| Таблица | Поля и ограничения |
|---|---|
| products | unique external_code VARCHAR(255), name TEXT, description TEXT (пустая разрешена), price/purchase_price/discount DECIMAL(18,2), created_at/updated_at TIMESTAMPTZ(0) |
| product_attributes | product_id FK, key VARCHAR(255), value TEXT; UNIQUE(product_id, key) |
| product_images | product_id FK, url VARCHAR(2048), path TEXT, position INTEGER >= 0; UNIQUE(product_id, url); индекс (product_id, position, id) |
| users | unique username VARCHAR(180), password_hash VARCHAR(255); открытый пароль в сущности/таблице отсутствует |

Все перечисленные поля NOT NULL. FK дочерних таблиц → products(id), ON DELETE CASCADE. Уникальные составные индексы начинаются с product_id и обслуживают поиск зависимостей. ORM настраивает cascade persist/remove и orphanRemoval; порядок изображений position/id, атрибутов key. Ведущие нули external_code сохраняются. Код/название/ключ/username не могут состоять только из обычных пробелов; path/hash/URL непустые. Полная нормализация/trim входных данных относится к последующим валидаторам, а не подменяется DB CHECK.

Выбранные технические границы хранения: external_code/key до 255 символов, username 180, hash 255. URL ограничен также 2048 **байтами UTF-8**, чтобы уникальный B-tree индекс имел ограниченный размер; сверхлимитные ссылки должны давать warning валидатора изображений загрузка изображений. Проверка HTTP(S)/SSRF/контента не выполняется схемой. name/description/value/path — TEXT без малого прикладного лимита. Эти решения не меняют публичную форму API; проверки до записи реализуются в соответствующих задачах.

## DECIMAL

Хранение и PHP hydration используют строки, без преобразования в float. price > 0, purchase_price >= 0, discount допускает минус. NaN запрещён для всех трёх полей. Вместимость DECIMAL(18,2): 16 целых и 2 дробных цифры; max 9999999999999999.99, min discount -9999999999999999.99, min price 0.01, min purchase_price 0.00. Выход за вместимость даёт SQLSTATE 22003; нарушение CHECK — 23514.

При непосредственной записи NUMERIC PostgreSQL округляет до scale 2: 1.005 → 1.01, -33.335 → -33.34 (проверяется тестом). Это защита хранения, а не реализация точного расчёта скидки или валидации строки валидация строк. валидация строк должна проверять вместимость и вычислять HALF_UP до INSERT, а не полагаться на округление БД. До flush/refresh объект содержит переданные конструктору строки; канонические два знака проверяются после чтения из БД.

## Запуск и проверки

PowerShell из корня проекта, Docker Linux Engine:

```powershell
$docker = 'docker'
& $docker compose build app
& $docker compose up -d --wait --wait-timeout 180
& $docker compose exec -T app php bin/console migrations:migrate --no-interaction
& $docker compose exec -T app php bin/console orm:validate-schema
python scripts/verify.py check
python scripts/verify.py test
```

Ожидаются код 0, миграция до Version20261101000100 (повтор безопасен), mapping correct и schema in sync, PASS check/test. При наличии Make эквиваленты — make migrate/schema-validate/check/test. Миграции не запускаются entrypoint автоматически.

Runner использует отдельный compose.test.yaml и tmpfs PostgreSQL. Lifecycle-тест сам создаёт уникальную БД product_import_test_rollback_*, проверяет пустоту, up, четыре metadata/schema sync, down до одной ledger-таблицы и повторный up, затем удаляет только созданную им БД. **Откат на рабочей БД не нужен для проверки схема БД:** он удаляет четыре таблицы и данные. Не запускать его через рабочий app и не удалять production volumes. Остальные тесты откатывают собственную транзакцию после каждого сценария. Подробности изоляции — [testing.md](testing.md).

## Расширение хранения хранение задач

Миграция Version20261102000100 добавляет import_jobs, import_row_results и import_issues; прежняя схема БД сохранена. Семь mapped tables проходят up/down/up и ORM schema sync. Jobs имеют owner FK users/RESTRICT; rows/issues FK job/CASCADE. PK (job,row_number) и issue fingerprint защищают от двойного учёта. Исторический product ID хранится в квитанции без FK. Три новых ORM модели readOnly; атомарные мутации выполняются DBAL Repository. [Колонки, ограничения, переходы и lease](import-jobs.md). Рабочая БД автоматически не мигрировалась.

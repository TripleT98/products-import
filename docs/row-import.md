# Импорт одного товара с изображениями

`App\Import\RowImportService::import(RowDto $row): RowImportResult` объединяет загрузка изображений и
запись товаров для одной уже валидированной строки. Ни очередь, ни HTTP-upload, ни чтение всего
файла, ни jobs/checkpoints в этот сервис не входят.

```php
$storage = App\Image\ImageStorage::fromEnvironment();
$service = new App\Import\RowImportService(
    new App\Image\ImageDownloader($storage),
    new App\Import\ProductWriter(),
    new App\Image\ImageFileCleaner($storage),
);
$result = $service->import($validatedRowDto);
```

Все компоненты должны использовать один IMAGE_DIR, а writer и cleaner — одну БД.
Для изолированной БД обоим передаётся одна фабрика свежих EntityManager. Каждый вызов
владеет своими короткими транзакциями; активная внешняя транзакция не поддерживается.

## Результат и ошибки

`RowImportResult` содержит:

- `write`: ProductWriteResult после commit, либо null при ошибке записи товара;
- `issues`: список RowIssue с severity/code/message, исходными rowNumber/externalCode
  и field images/product;
- `cleanupPendingPaths`: публичные пути файлов, очистка которых не подтверждена;
  их можно повторно передать ImageFileCleaner::clean. Это внутренние данные сервиса,
  без абсолютных серверных путей; долговечного учёта пока нет.

Все уникальные URL строки скачиваются до создания сессии записи товара. Неудачная
загрузка даёт warning; остальные изображения записываются. URL без успешного файла
не создаёт фиктивную связь. Для всё ещё указанного URL writer сохраняет прежнюю копию,
если она существует. Повтор DTO обновляет тот же товар и связи без дублей. Новая
успешная загрузка может заменить path существующей связи.

ProductWriter повторяет временные/unique-конфликты максимум три раза с новыми ORM
сессиями, используя уже подготовленные файлы: сеть внутри транзакций не вызывается.
После окончательной ошибки записи возвращается RowIssue error PRODUCT_WRITE_FAILED,
write=null; следующий товар можно обработать тем же сервисом. Непредвиденное исключение
также запускает очистку уже известных подготовленных файлов и пробрасывается вызывающему.

## Очистка и согласованность

Writer возвращает `obsoleteImagePaths` как необязательное дополнительное поле
ProductWriteResult (прежние три аргумента конструктора совместимы). Список вычисляется
под блокировкой товара и возвращается только после commit. Это позволяет не угадывать
прежние пути по устаревшему чтению до транзакции.

После успешного commit сервис проверяет новые и устаревшие пути. После rollback —
только новые подготовленные. Cleaner удаляет файл лишь при отсутствии ссылок с таким
path во всей таблице product_images, независимо от товара и исходного URL. Общая копия
сохраняется до удаления последней ссылки. Отсутствующий файл — успешный no-op.

ProductImageRepository получает пути/проверяет ссылки и берёт transaction-level
PostgreSQL advisory locks по hash публичного path. Writer удерживает блокировки всех
прежних и подготовленных путей до commit/rollback, сортируя ключи для согласованного
порядка. Cleaner удерживает ту же блокировку между проверкой ссылок и unlink.
READ COMMITTED даёт свежий snapshot после ожидания: незавершённая запись другого
товара не становится поводом удалить её файл. Конкурентный тест подтверждает это
двумя независимыми PHP-процессами и реальными PostgreSQL lock waits.

Протокол относится к управляемому импорту через ProductWriter/RowImportService.
Подготовленный дескриптор должен указывать на существующий файл; повторное ручное
подключение уже удалённого path или прямые SQL/ORM writes в обход протокола не являются
поддерживаемым импортом. Downloader всегда создаёт новые случайные имена, а сохранение
прежней копии опирается на существующую ссылку. HTTP write CRUD не добавлен.

ImageStorage удаляет только обычный файл внутри канонического IMAGE_DIR с безопасным
публичным именем/подкаталогом и расширением изображения; traversal, encoded paths,
staging и symlinks отклоняются. Файлы за пределами каталога не затрагиваются. В загрузка изображений
storage сам не удалял опубликованные файлы; в импорт строки добавлен явный guarded метод,
вызываемый cleaner после проверки БД. Downloader самостоятельно их не удаляет.

Если проверить БД или выполнить unlink невозможно, файл сохраняется, выдаётся warning
IMAGE_CLEANUP_FAILED и путь попадает в cleanupPendingPaths. Успешный commit товара
остаётся успешным: ошибка последующей очистки не превращается в ложный rollback и
не требует повторять запись товара. Повтор cleanup безопасен и снова проверяет ссылки.

## Проверки

Из PowerShell с работающим Docker Desktop Linux Engine:

```powershell
python scripts/verify.py check
python scripts/verify.py test
```

Ожидаются код 0, PASS и PHPUnit `OK (348 tests, ... assertions)`; фактические прогоны
в импорт строки дали 1702 assertions (счётчик ожиданий запись товаров может немного различаться). Общий контур
проверяет Composer, PHPStan level 5, стиль, миграции/schema, fixtures и frontend.
PHP/Composer/Make на хосте не нужны; Docker registry нужен при отсутствии кеша.

Десять тестов RowImportServiceTest работают с настоящим HTTP-сервером загрузка изображений, временными
реальными файлами и отдельной мигрированной PostgreSQL БД на каждый сценарий:

1. Несколько URL, один 404: warning с контекстом, остальные файлы/связи сохранены;
   повтор без дублей, старые заменённые файлы удалены.
2. Тот же URL стал недоступен: прежний path и SHA-256 сохранены; исчезнувшие URL
   удалены, без прежней копии не создана фиктивная ссылка.
3. Ошибка image insert после SQL товара/атрибутов: insert откатан, новых файлов нет;
   следующий товар записан.
4. Ошибка update: поля/атрибуты/связи полностью прежние; общий файл другого товара
   сохранил свои байты.
5. Общий path удаляется только после исчезновения последней ссылки.
6. Unique retry использует подготовленные файлы, без повторных HTTP-запросов;
   все запросы завершены до открытия writer-сессии.
7. Новая подготовленная копия успела стать ссылкой другого товара: rollback первой
   строки её не удаляет, остальные новые файлы очищены.
8. Ошибка проверки БД при cleanup: товар уже committed, warning и pending path
   возвращены; безопасная повторная очистка удаляет файл позже.
9. Небезопасные пути и symlink не удаляют целевой файл.
10. Пока другой writer держит path lock до INSERT/commit, cleaner реально ждёт;
    после commit видит новую ссылку и сохраняет файл, даже если прежняя ссылка
    была удалена во время ожидания.

Тестовый bootstrap запрещает рабочие реквизиты. Private БД и файловые каталоги,
дочерние процессы, test containers/network удаляются после проверки. Исходный XLSX,
внешние картинки и working volumes не используются.

## Оставшиеся ограничения

Нет долговечного списка cleanup retry, фонового scavenger и очистки после SIGKILL/
потери питания между публикацией файла и получением DTO либо после commit. Ошибка
cleanup сохраняет лишний файл вместо риска удалить используемый; caller может
повторить переданные pending paths. Нельзя обещать атомарность PostgreSQL и filesystem
при произвольном аварийном завершении. Такие восстановления требуют последующих
этапов; нормальные commit/rollback и проверяемые ошибки импорт строки покрыты.


## Optional checkpoint хранение задач

import принимает вторым необязательным аргументом ProductWriteCheckpoint, созданный
ImportJobService::checkpoint. Lease обновляется перед URL и после подготовки, вне
writer-транзакции. Warnings загрузок передаются атомарному receipt через withIssues.
При write=null caller явно вызывает recordFailure с errors; cleanup warnings/pending
paths сохраняет noteCleanup после commit. Без checkpoint прежнее поведение сохранено.
[Контракт, recovery и ограничения](import-jobs.md).

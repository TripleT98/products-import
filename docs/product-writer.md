# Атомарная запись товара

`App\Import\ProductWriter::write(RowDto $row, array $preparedImages): ProductWriteResult`
принимает валидный DTO из валидация строк и список `PreparedImage(url, path)` уже подготовленных
изображений. Сервис работает через `ProductRepository`, без HTTP, скачивания и операций
с файлами. Схема и публичный API не изменены. Зависимости fixtures/валидация строк проверены; требования
R03/R06 и правила сохранения прежних ссылок из R07 выполняются на уровне БД.

## Результат записи

- По `externalCode` создаётся товар либо обновляются его основные поля, включая точные
  decimal strings. Код и ID существующего товара, `createdAt` сохраняются; `updatedAt`
  обновляется.
- Атрибуты приводятся к полному текущему набору: одинаковые ключи обновляются,
  отсутствующие удаляются, новые добавляются. Значение `"0"` сохраняется. Сохранение
  существующих сущностей по ключу избегает промежуточного конфликта уникальности.
- Связи изображений приводятся к текущим `imageCandidates`, без повторных URL.
  `position` — исходный индекс кандидата; при пропущенной загрузке возможны пропуски
  индексов. Подготовленный дескриптор обновляет path, сохраняя исходный URL.
- Если текущий URL не имеет нового дескриптора, прежняя запись/path сохраняется.
  Если прежней записи нет, фиктивная связь не создаётся. Отсутствующие в текущем
  наборе URL удаляются из БД. Физические файлы здесь не удаляются.

`ProductWriteResult` содержит `productId`, `created` и `attempts`. Результат возвращается
после успешного commit. Дескриптор требует публичный `/images/...` path; абсолютный
серверный путь и traversal отклоняются. URL дескрипторов должны быть уникальны и
присутствовать среди кандидатов строки, иначе до записи возникает
`InvalidArgumentException`. Дескриптор не проверяет наличие или содержимое файла:
подготовка настоящих файлов относится к загрузка изображений/импорт строки.

## Транзакции и конкуренция

Одна запись товара со всеми атрибутами и связями изображений — одна транзакция.
Промежуточный flush основных полей/атрибутов не является commit: последующий сбой
изображений откатывает всё, включая удаления и timestamps. Ранее записанные товары
не откатываются. После ошибки тот же сервис способен записать следующий товар.

Каждая попытка получает собственный новый EntityManager и DBAL connection; после
попытки оба закрываются. По умолчанию используется `DoctrineFactory`; для отдельной
БД можно передать фабрику `Closure(): EntityManagerInterface`. Фабрика должна
возвращать свежую открытую сессию без активной транзакции. Встраивание в чужую
транзакцию не поддерживается: согласование checkpoint относится к хранение задач/восстановление.

Существующий товар блокируется `SELECT ... FOR UPDATE` до завершения транзакции.
Для одновременно создаваемого кода уникальный индекс PostgreSQL не допускает дубль.
Проигравшая попытка полностью откатывается и повторяет строку с новым EntityManager;
закрытая после ошибки ORM-сессия повторно не используется. Всего максимум три
попытки (настраивается в диапазоне 1–3), только для unique constraint и временных
DBAL `RetryableException`. Последняя успешно зафиксированная запись одного кода
побеждает целиком, включая атрибуты и связи.

При окончательном сбое выбрасывается `ProductWriteException` с кодом
`PRODUCT_WRITE_FAILED`, числом попыток и безопасным сообщением. Исходная причина
доступна внутреннему обработчику через `getPrevious()` и не предназначена для HTTP.
Перевод ошибки в issue строки/счётчики будет выполняться последующими задачами.

## Воспроизводимая проверка

Из корня проекта в PowerShell, при работающем Docker Desktop с Linux containers:

```powershell
python scripts/verify.py check
python scripts/verify.py test
```

Ожидается код 0, `PASS: check` / `PASS: test`, PHPUnit `OK (... tests, ... assertions)`; текущий общий набор после хранение задач содержит 348 тестов.
Число assertions может немного различаться из-за проверки состояния дочерних
процессов во время ограниченного ожидания. Make, PHP и Composer на хосте не нужны.
Образы собираются runner-ом; доступ к registry нужен при отсутствии локального cache.

`backend/tests/Integration/ProductWriterTest.php` содержит восемь сценариев запись товаров:
insert/повтор без дублей; полная замена/удаление атрибутов и ссылок; прежняя копия
при отсутствии дескриптора; отсутствие фиктивной новой ссылки; rollback insert и
update после реального SQL первого этапа; следующий товар после ошибки; лимит retries
с отдельными закрытыми сессиями; согласованность дескрипторов; конкурентная запись.
Некоторые проверки объединены в одном тестовом методе.

Конкурентный тест запускает два отдельных PHP-процесса и удерживает их на PostgreSQL
advisory gate после чтения отсутствующего товара. После снятия gate проверяется
реальный UNIQUE-конфликт: попытки `[1, 2]`, одинаковый product ID, один insert и один
update, итоговые поля/атрибут/изображение принадлежат последнему writer целиком.
Ожидания ограничены timeout; внешние URL не открываются.

Контур изолирован от приложения: PostgreSQL tmpfs, internal network, отдельная БД
`product_import_test_writer_<random>` для каждого теста. Дочерний helper отказывается
работать с другим именем БД и дополнительно проходит общий test bootstrap. В конце
проверочные БД, контейнеры и сеть удаляются. Тестовые path — только метаданные, без
создания файлов. Подробности общего контура: [testing.md](testing.md).

Загрузчик, очистка файлов, orchestration строки, jobs/checkpoints, worker и интерфейс
импорта в запись товаров не реализуются. Работающий сервис на порту 8080 автоматически не
пересобирается и не мигрируется.


В импорт строки ProductWriteResult дополнен optional obsoleteImagePaths: пути, исчезнувшие из
текущего набора, возвращаются только после commit. Writer берёт sorted advisory locks
по прежним/подготовленным path, согласованные с ImageFileCleaner. Сам writer по-прежнему
не выполняет HTTP/unlink. [Объединение строки и безопасная очистка импорт строки](row-import.md).


В хранение задач optional ProductWriteCheckpoint добавляет job/row result к той же транзакции.
До товарных SQL проверяется lease/replay, после flush записываются receipt/issues/counters;
сбой checkpoint откатывает товар. Без checkpoint режим запись товаров/импорт строки сохранён.
[Хранение задач и новый контракт](import-jobs.md).

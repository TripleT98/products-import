# Валидация строк XLSX

RowValidator нормализует данные книги и возвращает DTO и ошибки строк. Правила описаны в [формате импорта](import-format.md). Валидация не выполняет сетевые запросы и не записывает товары.

## Программный результат

`RowValidationService::validate(iterable<WorkbookRow>)` даёт Generator<RowResult>. В каждом результате rowNumber, dto (RowDto или null), список RowIssue. Пустые строки пропускаются. Новый вызов service начинает новый набор дубликатов; один и тот же service можно использовать для другого файла. RowValidator можно вызвать отдельно для одной строки.

RowDto содержит rowNumber, externalCode/name/description, точные исходные десятичные sale/purchase в нормализованной записи, канонические price/purchasePrice/discount, упорядоченные пары attributes [{key,value}] и imageCandidates [URL]. Это внутренний DTO, не новый публичный API response. Коды/имена/описание обрабатываются как текст, не HTML/инструкции.

RowIssue: severity, code, message, rowNumber, externalCode (null, если корректный код определить не удалось), field. field — camelCase или attributes.<key>/images. В сообщении нет raw cell/formula/URL. Persistent id ещё отсутствует: он появится при сохранении issues хранение задач, публичный ImportIssue из OpenAPI не изменён.

Возвращается первая ошибка строки в стабильном порядке: код, имя, описание, числа/знаки/вместимость, атрибуты. Такая строка не имеет DTO. У валидного DTO может быть несколько warning по изображениям. Ошибки строк не прерывают поток; ошибка структуры headers остаётся фатальной WorkbookException.

## Текст, коды и атрибуты

- Trim крайних Unicode-пробелов/BOM; код/имя обязательны, описание по умолчанию пустая строка. NUL/невалидный UTF-8 отклоняются; булевы/error cells в основных полях недопустимы. Текстовые externalCode сохраняют ведущие нули.
- Числовой код должен быть целым. General даёт обычную целочисленную запись без экспоненты; простой формат 000000 сохраняет заданную ширину. Другие числовые форматы считаются неоднозначными, ошибка INVALID_EXTERNAL_CODE. Длина кода до 255 Unicode-символов согласно схема БД; превышение VALUE_TOO_LONG. Текстовые name/description не получают малого скрытого лимита.
- Headers по-прежнему нормализует HeaderMapper чтение XLSX. Для ключей Доп. поле дополнительно проверены 255 символов/NUL до выдачи строк; пустые/повторные/слишком длинные keys дают INVALID_HEADERS. Доп. поле Размер и Доп. поле: Размер эквивалентны. Ключи регистрозависимы, новые колонки не требуют изменения кода.
- Значения атрибутов trim-ятся, пустые пропускаются; 0 сохраняется. Numeric значения остаются исходными строковыми лексемами; bool атрибута явно становится TRUE/FALSE, не исчезает из-за false. Error cell в атрибуте даёт INVALID_ATTRIBUTE_VALUE. Формула в любом импортируемом поле, включая атрибуты и источники изображений, — FORMULA_NOT_ALLOWED; cached value не используется. Формулы в игнорируемых стандартных колонках не вычисляются и не импортируются.

## Точная арифметика

brick/math 1.0.0: BigDecimal для исходных сумм и BigRational для discount. Ни одного промежуточного float. Текст принимает десятичную точку/запятую, группировку тысяч обычным/NBSP/узким NBSP по три цифры, минус в начале. Валютные символы, смешанные точка/запятая и текстовая экспонента отклоняются. Числовая OOXML-ячейка может содержать scientific notation — она точно разбирается из лексемы чтение XLSX.

Точка/запятая всегда десятичная, а не разделитель тысяч: 1,320 означает 1.320 → 1.32, не 1320. Это следует из принятого правила не угадывать тысячный разделитель и разрешать больше двух дробных знаков. Для тысяч используются только пробелы корректными группами.

price raw > 0, purchase raw >= 0. Оба хранимых значения округляются HALF_UP до двух знаков; price после округления тоже >0. Discount вычисляется как (raw sale − raw purchase) / raw sale ×100 точной рациональной дробью и округляется один раз в конце. Не использовать округлённые price/purchasePrice как операнды формулы.

Примеры: 3/1 → 66.67%, 3/4 → -33.33%; sale=200/purchase=180.01 → 10.00%, purchase=219.99 → -10.00%. Для 1.005/0.995 хранятся 1.01/1.00, discount=1.00 (по raw values). Отрицательный ноль канонизируется в 0.00.

Вместимость проверяется после обязательного округления до scale=2: max abs 9999999999999999.99 для всех трёх полей. Например 9999999999999999.994 округляется в max и допустимо; .995 переполняет. Слишком большой discount тоже ошибка строки DECIMAL_OUT_OF_RANGE. Отрицательные исходные price/purchase не принимаются даже при округлении в 0.00.

Технический ресурсный предел parse — 4096 цифр десятичного представления (с учётом раскрытия exponent), через безопасный BigDecimal::parse. Это защита от гигантских exponent/precision, не обещание неограниченного размера чисел; превышение даёт DECIMAL_OUT_OF_RANGE. Лимиты книги чтение XLSX сохраняются.

## Дубликаты и URL

Первая полностью валидная DTO-строка резервирует нормализованный externalCode в пределах файла. Предыдущая невалидная строка его не резервирует. Предупреждения URL не делают DTO невалидным. После резервирования любая следующая строка с тем же корректно определимым кодом получает DUPLICATE_EXTERNAL_CODE до остальной проверки; первая строка не заменяется. Будущая ошибка записи не освобождает код — stream не зависит от результата БД.

ImageCandidateExtractor берёт нормализованные атрибуты Ссылка на упаковку, затем Ссылки на фото, независимо от расположения колонок. Делит по запятой, trim, удаляет повторы внутри товара с сохранением первого порядка. Дедупликация точная по строке URL, без догадок о канонизации. Исходная trim-строка ссылочного поля остаётся обычным атрибутом.

Только синтаксически корректные HTTP/HTTPS URI до 2048 UTF-8 байт дают кандидата. Ошибка scheme/URL/длины → IMAGE_URL_REJECTED warning, товар остаётся валидным. Повтор одного некорректного URL в товаре не множит warning. На этом этапе нет DNS/IP/redirect/SSRF/загрузки/проверки изображения: эти проверки выполняются до сети в загрузка изображений. Даже syntactically valid private адрес здесь лишь кандидат, сетевого запроса не происходит. Количество кандидатов не означает успешное скачивание.

## Диагностика и самостоятельная проверка

```powershell
python scripts/verify.py check
python scripts/verify.py test
python scripts/check-workbook.py --xlsx 'path/to/workbook.xlsx' --sample --validate
```

Ожидаются код 0 и PASS. Последняя команда строит production image product-import-workbook:t10 и запускает `APP_ENV=development php bin/console workbook:inspect /input/workbook.xlsx --validate` в контейнере --network none, с исходником read-only и недоступным DB_HOST. Итог:

Unit tests покрывают искусственные числа/группировку/округления/нули/пределы и ошибки типов/формулы, коды и форматирование, динамические атрибуты/0, URL-order/dedup/warnings, первые валидные дубликаты и продолжение потока. Дополнительный XLSX roundtrip проходит настоящий чтение XLSX reader с переставленными колонками, numeric code mask и формулой в атрибуте. Старые Unit/Integration/API и frontend проверки остаются в общем check/test. Исходный пользовательский XLSX не нужен для обычного check/test, не копируется в Git и никогда не перезаписывается.

Фактические результаты — статус. Расчёт скидки опирается на [официальный brick/math](https://github.com/brick/math) и API фактически установленного 1.0.0.
